# proxylog

AquariusProxy incoming-chat logging: viability of a log-tailing chat collector vs. a plugin, plus the native-image plugin short-circuit

## Findings

- **[verified]** Incoming server chat reaches three inbound handlers registered in the client codec: ClientboundSystemChatPacket -> SystemChatHandler, ClientboundPlayerChatPacket -> PlayerChatHandler, ClientboundDisguisedChatPacket -> DisguisedChatHandler. There is no ClientboundChatPacket (legacy 1.12) handler anywhere in the fork, so pre-1.19 chat must be up-converted by ViaVersion before it reaches these handlers.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/network/codec/PacketCodecRegistries.java:147-148 and :196; zero grep hits for 'ClientboundChatPacket' across src/main/java

- **[verified]** The chat log statements are exactly: SystemChatHandler.java:99 (CHAT_LOG.info(component) inside logSystemChat), PlayerChatHandler.java:34, DisguisedChatHandler.java:31 - plus two non-server sources on the same logger: Proxy.java:869 (proxy-internal PrivateMessageSendEvent echo to connected clients) and ExtraChat.java:93 (synthesized 'Position in queue: N' line).
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/network/client/handler/incoming/SystemChatHandler.java:88-100; .../PlayerChatHandler.java:33-35; .../DisguisedChatHandler.java:30-32; .../Proxy.java:869; .../module/impl/ExtraChat.java:91-94

- **[verified]** CHAT_LOG is the slf4j logger literally named 'Chat', so with %logger{36} the prefix token in every line is [Chat]. Log level is INFO for all chat lines.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/Globals.java:59 (ComponentLogger.logger("Chat"))

- **[verified]** File line format is exactly '[yyyy/MM/dd HH:mm:ss] [Chat] [INFO] <chat text>' + newline. Local time, second resolution, no timezone offset. debug.log uses the same layout with millisecond precision (HH:mm:ss.SSS).
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/resources/logback.xml:21 (latest.log pattern) and :45 (debug.log pattern); a real line's masked prefix from an existing log read as [9999/99/99 99:99:99] [Proxy] [INFO]

- **[verified]** Chat text in the FILE is plain: the ComponentLogger provider serializes the Adventure Component to ANSI escapes (serializeAnsi), and the file encoder's custom %stripAnsi converter regex-strips every ANSI sequence before writing. So no section codes, no ampersand codes, no ANSI in latest.log - all color/formatting information is destroyed. The TERMINAL appender uses %msg and therefore keeps the ANSI colors.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/terminal/AquariusComponentLoggerProvider.java:26 (helper.delegating(backing, ComponentSerializer::serializeAnsi)); .../terminal/logback/AnsiStripConverter.java:9-19; .../terminal/logback/AnsiStripEncoder.java:18; logback.xml:20-22 vs :68-70

- **[verified]** Chat logging is ON BY DEFAULT. The gate is CONFIG.client.extra.logChatMessages, declared 'public boolean logChatMessages = true'. A tailer works out of the box on a default config. It is runtime-togglable via the 'extrachat logChatMessages on/off' and 'terminal logChatMessages on/off' commands, so a collector should not assume it stays on.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/util/config/Config.java:157; gate checks at SystemChatHandler.java:89, PlayerChatHandler.java:33, DisguisedChatHandler.java:30; toggles at command/impl/ExtraChatCommand.java:84-88 and command/impl/TerminalCommand.java:44-48

- **[verified]** A second flag suppresses system chat while the bot is IN QUEUE: CONFIG.client.extra.logOnlyQueuePositionUpdates (default true) makes logSystemChat return early for the whole queue period, and ExtraChat instead emits a synthesized gold 'Position in queue: N' line on the same [Chat] logger. When that flag is false, queue system chat IS logged but with literal '\n\n' sequences stripped from the component.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/util/config/Config.java:158; SystemChatHandler.java:91-98; ExtraChat.java:92-93

- **[verified]** The [Chat] logger is NOT chat-only. SystemChatHandler logs BEFORE any parsing (line 99 precedes the ChatSchemaParser call at line 54), so every non-overlay system message - death messages, server broadcasts, command output, whisper text, join/leave spam, restart notices - lands on [Chat] [INFO] indistinguishably. Only action-bar/overlay text is excluded (packet.isOverlay() early return).
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/network/client/handler/incoming/SystemChatHandler.java:35-38 and :54-81 vs the log call at :99

- **[verified]** The logged line contains ONLY the display name, never a UUID. For system chat the logged component is the server's raw rendered text; for player chat the logged component is chatType.render(packet.getName(), ...) which embeds the display-name component. The sender UUID exists in-process (PublicChatEvent.sender() is a PlayerListEntry with getProfileId(); PlayerChatHandler resolves it from packet.getSender() against the tab-list cache) but is never written to the log. A log-tailing corpus is therefore name-keyed only and will be corrupted by renames / name reuse.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/network/client/handler/incoming/PlayerChatHandler.java:24-34; .../event/chat/PublicChatEvent.java (sender is PlayerListEntry); .../database/ChatDatabase.java:52 shows the UUID is available in-process via event.sender().getProfileId()

- **[verified]** Whispers/DMs go through the SAME CHAT_LOG.info path as public chat with no type marker - the log line is just the server's rendered text. They are distinguishable only by re-parsing the text against the chat schema. Default schema (used for every server, including 2b2t, because the serverSchemas override map is empty by default) is publicChat '<$s> $m', whisperInbound '$s whispers: $m', whisperOutbound 'to $r: $m'. A collector must reimplement that discrimination itself; the proxy does not label the line.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/feature/chatschema/ChatSchema.java:8-12; ChatSchemaParser.java:29-51 (getSchema falls back to DEFAULT_SCHEMA); Config.java:99-101 (serverSchemas is an empty LinkedHashMap by default); SystemChatHandler.java:99 logs before the parse at :54

- **[verified]** The proxy's own schema parse is stricter than a regex tailer can be: ChatSchemaParser only accepts a sender/receiver if the name resolves in the tab-list cache, otherwise it returns null and the message is downgraded to a generic SystemChatEvent. A log tailer has no tab list, so its whisper/public classification will diverge from the proxy's on unresolvable names.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/feature/chatschema/ChatSchemaParser.java:130-153 (getFromName -> return null on empty) and :171-189

- **[verified]** Log layout: active file is 'log/latest.log' relative to the process working directory (each bot's install dir); archives are 'log/proxy-yyyy-MM-dd.N.log.zip'. Rotation is TimeBasedRollingPolicy with a size+time trigger at MaxFileSize 250MB, maxHistory 1000, totalSizeCap 250MB, cleanHistoryOnStart=true. The zip contains a single entry named proxy-yyyy-MM-dd.N.log.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/resources/logback.xml:18-36; verified against a real archive: unzip -l of a proxy-*.log.zip lists one .log entry

- **[verified]** A tailer MUST handle rotation mid-stream, and specifically must handle rotation on EVERY proxy restart: StartupSizeAndTimeBasedTriggeringPolicy forces isTriggeringEvent to return true on the first logging event of the process, so latest.log is rolled away into a zip and recreated at each startup. Combined with daily + 250MB rollovers, an inode-pinned tail will silently go dead. Observed empirically: the local dev latest.log contained exactly 1 line (a fresh post-startup roll).
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/terminal/logback/StartupSizeAndTimeBasedTriggeringPolicy.java:12-20; wc -l on C:/Users/hellj/ZenithProxy/run/log/latest.log = 1 with ~30 archived proxy-*.log.zip siblings

- **[verified]** The file appender is lazily started (LazyInitRollingFileAppender) and is a no-op only during native-image BUILD time - it appends normally at native-image runtime. So file logging works identically on the java and linux (native) channels; a tailer is channel-agnostic.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/terminal/logback/LazyInitRollingFileAppender.java:12-27 (guards on ImageInfo.inImageBuildtimeCode only)

- **[verified]** Archived zips can be deleted out from under a backfill job: Proxy.clearOldLogs() walks log/ and deletes every *.zip 10s after startup, gated by CONFIG.debug.clearOldLogs which defaults to false. Logback's own cleanHistoryOnStart=true also prunes on start per maxHistory/totalSizeCap.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/Proxy.java:158 and :242-254; Config.java:3013 (clearOldLogs = false); logback.xml:30

- **[verified]** Chat also flows to debug.log with millisecond timestamps whenever CONFIG.debug.debugLogs is on ([Chat] passes the TRACE threshold and the LogSourceFilter allows 'Chat' at TRACE). That is a higher-resolution but much noisier tail target.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/resources/logback.xml:42-61; terminal/logback/LogSourceFilter.java:27 (Chat -> Level.TRACE); terminal/logback/DebugLogConfigurationFilter.java:16-22 (gated on CONFIG.debug.debugLogs)

- **[verified]** EXISTING built-in chat-to-storage feature that could be enabled instead of writing a tailer: ChatDatabase subscribes to PublicChatEvent and INSERTs (time, chat, player_name, player_uuid) into a Postgres 'chats' table - i.e. it captures the UUID that the log line lacks. It skips non-2b2t servers and skips while in queue.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/database/ChatDatabase.java:48-66; database/dto/records/ChatsRecord.java:7

- **[verified]** That database route is OFF by default and has heavy infra prerequisites: CONFIG.database.enabled defaults to false (chatsEnabled defaults true but is only consulted when enabled), it extends LiveDatabase which requires a Redis/Redisson connection for the cross-instance lock and live topic, and the proxy does NOT provision the 'chats' table - the only bundled schema SQL is for the stash system.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/util/config/Config.java:3314-3341 (enabled=false, chatsEnabled=true, Lock.redisAddress); database/DatabaseManager.java:46-47; database/LiveDatabase.java:37-62; only src/main/resources/stash/schema.sql exists, no chats DDL

- **[verified]** Second existing feature, not a persistence option: module ChatHistory keeps only an in-memory CircularFifoQueue replayed to clients on login (default enable=false, maxCount 10, 30s window, cleared on disconnect). Third: the Discord chat relay (CONFIG.discord.chatRelay) forwards chat events to a Discord channel. Neither writes a structured chat file.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/module/impl/ChatHistory.java:22-95; Config.java:3140-3145 (enable=false); discord/ChatRelayEventListener.java:44-56; Config.java:3262-3265

- **[verified]** There is no HTTP/websocket chat surface built in. The only embedded servers are CommandHttpServer (permissions), ViewerHttpServer, RbacApiServer and ViewerApiServer, and grepping them for 'chat' returns nothing.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/feature/viewer/ViewerHttpServer.java and module/impl/ViewerApiServer.java - case-insensitive grep for 'chat' yields zero hits

- **[verified]** CONFIRMED: PluginManager short-circuits plugin-jar loading under GraalVM native-image runtime. preLoadPlugins() checks ImageInfo.inImageRuntimeCode() and, if true, only fires a Discord 'Potential Plugins Found / plugins are not supported on the linux release channel' embed and returns - findPotentialPluginJars/preLoadPotentialPluginJar never run, so no plugin in plugins/ is loaded on the linux (native) channel. A plugin-based chat collector would silently collect nothing on native-image bots.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/plugin/PluginManager.java:122-137, guard at :124; warning body at :92-110

- **[verified]** One nuance to the short-circuit: preLoadPluginsFromSystemClasspath() is called at line 123, BEFORE the native-image guard at :124, and it discovers plugins by scanning the system classloader for 'zenithproxy.plugin.json'. So a collector compiled INTO the image / onto the classpath would still load on native; only external jars dropped in plugins/ are skipped. ImageInfo.inImageRuntimeCode() is just a check of the system property org.graalvm.nativeimage.imagecode == 'runtime'.
    - _evidence:_ C:/Users/hellj/ZenithProxy/src/main/java/com/aquarius/plugin/PluginManager.java:122-123 and :149-160; util/ImageInfo.java:94-96

- **[verified]** The fork is byte-identical to stock upstream on every point above: same default logChatMessages=true, same logback.xml file names/patterns/rolling policy, same CHAT_LOG.info call sites and line numbers, and the same ImageInfo.inImageRuntimeCode() guard at PluginManager.java:124. Only the package root differs (com.aquarius vs com.zenith).
    - _evidence:_ C:/Users/hellj/zenithproxy-upstream/src/main/java/com/zenith/util/config/Config.java:150-151; upstream src/main/resources/logback.xml:19,21,24,43,45,48,69; upstream SystemChatHandler.java:99 and PlayerChatHandler.java:34; upstream plugin/PluginManager.java:124

## Unknowns
- No real [Chat] line was available to sample: the local dev log dir (ZenithProxy/run/log) has a 1-line latest.log and none of its ~30 archived zips contain a [Chat] match, and the auto-miner/logs/*.gz files are Minecraft client logs, not proxy logs. The format above is derived from the logback pattern + the provider's serializer, not observed on a live chat line.
- Which of the three handlers actually fires on 2b2t is unverified from source. 2b2t is a 1.12.2 server behind ViaVersion, so chat almost certainly arrives as ClientboundSystemChatPacket (SystemChatHandler, the no-UUID path), but the Via translation was not traced in the via/ package. If any bots run a modern server where ClientboundPlayerChatPacket is used, the log line is still name-only but the in-process event carries the signed sender UUID.
- Whether embedded newlines inside a chat component are escaped anywhere before the encoder. Nothing in AnsiStripConverter or the pattern escapes them, so a multi-line system message should write N physical lines with only the first carrying the [Chat] prefix - likely, but not observed in a real file.
- Whether slf4j placeholder interpretation can mangle chat text containing literal {} - ComponentLogger.info(Component) forwards a pre-serialized message with no varargs, so it should pass through untouched, but this was not tested.
- Whether the deployed ABM fleet actually runs with default logChatMessages/logOnlyQueuePositionUpdates values, or whether per-bot config.json files have toggled them (real bot config files were not read).
- The exact 2b2t public-chat prefix shape as it appears post-Via (rank prefixes, whether it literally matches '<$s> $m'), which determines the collector's regex. The default schema in the source says '<$s> $m' but no live line was seen to confirm.

## Build implications
- A tailer works with zero deploy and zero config change: chat logging is ON by default (Config.java:157) and file logging works on both the java and linux/native channels. Tail <bot install dir>/log/latest.log.
- Match lines with an anchored regex on the fixed prefix: ^\[(\d{4}/\d{2}/\d{2} \d{2}:\d{2}:\d{2})\] \[Chat\] \[INFO\] (.*)$ . Treat any line that does NOT match that prefix as a continuation of the previous event (embedded newlines in a component produce unprefixed physical lines) - do not drop them blindly or multi-line system messages will silently truncate.
- MUST handle rotation on every restart, not just daily. StartupSizeAndTimeBasedTriggeringPolicy forces a roll on the first log event of each process, so latest.log is moved into log/proxy-yyyy-MM-dd.N.log.zip and recreated at every proxy start. Poll by (path, size, and dev/inode or file identity); on shrink-or-replace, drain the old handle then reopen latest.log from offset 0. Never pin the inode.
- For backfill, read the zip archives: log/proxy-yyyy-MM-dd.N.log.zip, one entry per zip named proxy-yyyy-MM-dd.N.log, same line format. Copy them out promptly - logback prunes on start (cleanHistoryOnStart, maxHistory 1000, totalSizeCap 250MB) and Proxy.clearOldLogs() deletes all zips 10s after startup if CONFIG.debug.clearOldLogs is ever turned on.
- Do not expect ANSI or section codes: the file writer strips all ANSI and the component is flattened, so formatting/color is unrecoverable from the log. If the collector needs rank colors or click/hover data, the log route cannot supply it - only the in-process Component can.
- Key up front, in the schema: log-derived records are NAME-ONLY. There is no UUID anywhere in the line. Renames and name reuse will merge/split identities and corrupt the corpus over time. Either accept a name-keyed corpus with an explicit 'identity unresolved' caveat, or plan a side-channel that resolves name->UUID at capture time (tab list snapshot) or after the fact (Mojang API / third-party name history).
- The collector MUST filter, not assume: [Chat] carries all system messages (death messages, broadcasts, join/leave, restart notices, command output) plus proxy-generated lines - Proxy.java:869 DM echoes and ExtraChat.java:93 'Position in queue: N'. Whitelist by matched chat shape rather than blacklisting noise.
- Exclude private messages by reimplementing the default ChatSchema in the tailer: inbound whisper '$s whispers: $m', outbound whisper 'to $r: $m', public '<$s> $m'. Test whisper patterns BEFORE the public pattern (that is the order ChatSchemaParser uses) and drop anything matching either whisper form. Sender/receiver token charset is [\w\d_.]+ and the message token is greedy (.+).
- Also handle per-server schema overrides: if CONFIG.client.chatSchemas.serverSchemas has an entry for the connected address, the proxy uses that instead of the default - a robust collector should read the bot's config.json and use the configured schema for that server key rather than hardcoding the default.
- Accept that log-based whisper exclusion is best-effort: the proxy resolves sender/receiver against the live tab list and refuses the parse when the name is unknown, which a tailer cannot replicate. Prefer false-negative on 'is public chat' (drop ambiguous lines) so private text never enters the corpus.
- If UUID fidelity actually matters, do not build the tailer - enable the existing ChatDatabase instead: it already writes (time, chat, player_name, player_uuid) per PublicChatEvent and excludes queue and non-2b2t traffic. Cost: set CONFIG.database.enabled=true plus host/port/username/password, stand up Redis for the Redisson lock/topic, and hand-create the 'chats' table (the proxy ships no DDL for it - only stash/schema.sql).
- Do not consider a plugin for native-image bots: PluginManager.java:124 returns before jar discovery under GraalVM runtime, so a plugin collector shipped as a jar in plugins/ collects nothing and only emits a Discord warning. Either restrict the plugin to java-channel bots, or compile the collector onto the classpath so preLoadPluginsFromSystemClasspath (called at :123, before the guard) still picks it up via its zenithproxy.plugin.json.
- Guard against silent capture loss: logChatMessages is runtime-togglable via the extrachat/terminal commands, so a live operator can turn the feed off with no error. The collector should alarm on an unexpectedly long gap in [Chat] lines rather than treating silence as quiet chat.
- ChatHistory (in-memory, 10 messages, 30s, default off) and the Discord chatRelay are not viable capture backends - do not build on them.
