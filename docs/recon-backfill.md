# backfill

Backfilling gaps in a live 2b2t chat capture via GET https://api.2b2t.vc/chats/window (source-verified against rfresh2/2b2t.vc-api @ 5875597, plus ~90 live probes)

## Findings

- **[verified]** startDate/endDate on /chats/window are bound as java.time.LocalDateTime with @DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME), which Spring maps to the lenient DateTimeFormatter.ISO_DATE_TIME. Accepted forms (all HTTP 200 live): yyyy-MM-dd'T'HH:mm (minutes only), ...HH:mm:ss, ...HH:mm:ss.SSS, ...HH:mm:ss.SSSSSS (micros), ...HH:mm:ss.SSSSSSSSS (nanos). The Swagger text claiming 'yyyy-MM-dd'T'HH:mm:ss.SSSXXX' understates what is accepted; .SSS is sufficient but NOT the only form.
    - _evidence:_ src/main/java/vc/controller/ChatsController.java:175-176 (@DateTimeFormat(iso = DateTimeFormat.ISO.DATE_TIME) LocalDateTime startDate/endDate); doc string at :152. Live: startDate=2023-01-01T00:00 / T00:00:00 / T00:00:00.000 / .000000 / .000000000 each returned 200 with identical first row 2023-01-01T00:00:05.309Z.

- **[verified]** A trailing zone/offset on the bound is PARSED BUT SILENTLY DISCARDED, because the target type is LocalDateTime (no offset field). '...T00:00:00.000Z', '+00:00', '-05:00' and '+09:00' all produce byte-identical result sets. Bounds are therefore always interpreted as UTC wall-clock regardless of what offset you send — sending a local offset silently queries the wrong instant.
    - _evidence:_ ChatsController.java:175-176 binds to LocalDateTime; :216/:218/:224/:226 call startDate.atOffset(ZoneOffset.UTC). Live: the four offset variants of window 2023-01-01T00:00:00.000..T00:10:00.000 all returned first=2023-01-01T00:00:05.309Z last=2023-01-01T00:00:12.873Z.

- **[verified]** A date-only value (e.g. startDate=2023-01-01) is NOT accepted on /chats/window — unlike /chats, which uses ISO.DATE and LocalDate. This is an easy cross-endpoint mistake.
    - _evidence:_ ChatsController.java:96-97 (/chats uses ISO.DATE + LocalDate) vs :175-176 (/chats/window uses ISO.DATE_TIME + LocalDateTime). Live: startDate=2023-01-01 on /chats/window returned HTTP 302, not 200.

- **[verified]** CRITICAL FAILURE MODE: an unparseable date does NOT return 400. It produces HTTP 302 with Location: https://api.2b2t.vc/ , which redirects to /scalar and yields HTTP 200 with an HTML API-explorer page. A redirect-following HTTP client therefore sees 200 + text/html for a malformed request, and a naive collector will read that as success or as an empty result.
    - _evidence:_ src/main/java/vc/controller/ErrorHandlerController.java (@RequestMapping("/error") returns "redirect:/") + HomepageController.java (@RequestMapping("/") returns "redirect:/scalar"). Live with redirects disabled: space-separator, date-only, 'notadate', and epoch-millis bounds each returned 302 Location=https://api.2b2t.vc/. Live with redirects followed: 200, Content-Type text/html, body beginning '<!doctype html>... <title>2b2t.vc API Explorer</title>'.

- **[verified]** Controller-level validation failures return a clean HTTP 400 with a completely empty body and no Content-Type: missing sort anchor, endDate<=startDate, and pageSize>100. These are distinguishable from the 302 parse-failure path.
    - _evidence:_ ChatsController.java:181-183 (pageSize>100 -> badRequest), :186-190 (endDate.equals(startDate) || endDate.isBefore(startDate) -> badRequest), :194-196/:202-204 (missing anchor -> badRequest). Live: HTTP=400, Content-Type absent, body length 0 for all five cases.

- **[verified]** BOTH window bounds are INCLUSIVE. ASC builds time >= startDate AND (optionally) time <= endDate; DESC builds time <= endDate AND (optionally) time >= startDate. There is no exclusive end. Consequence: naive window stitching where the next startDate equals the previous last-seen timestamp WILL re-deliver that boundary row, and dedupe is mandatory — it is not optional hygiene.
    - _evidence:_ ChatsController.java:216-218 (greaterOrEqual(startDate) / lessOrEqual(endDate)) and :224-226 (lessOrEqual(endDate) / greaterOrEqual(startDate)). Live: ASC startDate == a known row's exact timestamp returned that row as element 0; startDate one unit later excluded it; ASC endDate == a known row's timestamp still included that row as the last element; DESC endDate == the window's last row's timestamp returned it as element 0.

- **[verified]** The inclusive comparison is honored at FULL MICROSECOND resolution, not milliseconds. For a real row at ...T20:17:52.872508Z: startDate=...872508 -> row returned; startDate=...872509 (+1 microsecond) -> HTTP 204; startDate=...872 (ms floor) -> row returned; startDate=...873 (ms ceiling) -> HTTP 204. Advancing a cursor by +1ms, or formatting the cursor with only 3 fractional digits and rounding up, silently DROPS every row inside that millisecond.
    - _evidence:_ Live probes against endDate=2026-07-25T20:18:20.000&sort=ASC. Column type is SQLDataType.TIMESTAMPWITHTIMEZONE(6) per src/main/java/vc/data/dto/tables/Chats.java:44 (Postgres timestamptz(6) = microsecond).

- **[verified]** sort=ASC requires startDate (400 without it); sort=DESC requires endDate (400 without it). Supplying BOTH is fully legal and applies both as bounds, with sort choosing only the direction and the required anchor. Supplying NEITHER is a 400 because sort defaults to ASC and then startDate is missing.
    - _evidence:_ ChatsController.java:184 (sort defaults to ASC), :192-209 and :211-229 (per-sort anchor checks, duplicated). Live: 'ASC no startDate' 400; 'DESC no endDate' 400; 'no params at all' 400; both+ASC 200 ascending from window start; both+DESC 200 descending from window end; both+no-sort 200 ascending.

- **[verified]** A zero-width window is rejected: endDate exactly equal to startDate returns 400 (not an empty 204). A collector that computes start==end for a zero-length gap must skip the call rather than issue it.
    - _evidence:_ ChatsController.java:186-190; live startDate=endDate=2023-01-01T00:00:00.000 returned HTTP 400 with empty body.

- **[verified]** /chats/window returns ONLY {"chats":[...]}. There is no total, no pageCount, no hasMore, and no next-cursor — confirmed both in the record definition and in every live 200 response (top-level keys were always exactly ['chats']). /chats does return total and pageCount; /chats/window deliberately does not.
    - _evidence:_ ChatsController.java:52 (record ChatWindowResponse(List<PlayerChat> chats)) vs :51 (record ChatSearchResponse(List<PlayerChat> chats, int total, int pageCount)); :242 returns new ChatWindowResponse(chats). Live: TOPKEYS=['chats'] on ~25 distinct successful requests.

- **[verified]** End-of-window is signalled two ways and a consumer must handle both: (a) HTTP 204 No Content with an empty body when the page contains zero rows, and (b) HTTP 200 with a short page, i.e. len(chats) < pageSize. There is never a 200 with an empty array.
    - _evidence:_ ChatsController.java:239-241 (if (chats.isEmpty()) return ResponseEntity.noContent()). Live 204s: future window 2030-01-01..2030-01-02; open-ended ASC startDate=2030-01-01; page offset past the row count. Live short page: open-ended ASC startDate=<4 min ago>&pageSize=100 returned 200 with N=12.

- **[verified]** page is 1-indexed via offset = max(0, page-1) * pageSize, so page omitted, page=0 and page=1 are all the SAME first page. Default pageSize is 25; the documented max of 100 is enforced only on the upper side (pageSize=101 -> 400). pageSize=0 is NOT rejected and yields HTTP 204 (indistinguishable from 'no data'); pageSize=-1 produces the 302 error-redirect path.
    - _evidence:_ ChatsController.java:230 (var offset = (page == null ? 0 : Math.max(0, page - 1)) * size), :185 (size = pageSize == null ? 25 : pageSize), :181-183 (only pageSize > 100 checked — note /chats at :102 checks both bounds). Live: page absent/0/1 all returned the same two rows; page=2 returned the next two; page=3 the next two; pageSize=101 -> 400; pageSize=0 -> 204; pageSize=-1 -> 302; no pageSize -> N=25.

- **[verified]** Deep pagination within one window is consistent and non-overlapping. Offset 200 reached via pageSize=50&page=5 returned rows tuple-identical to the first 50 rows of pageSize=100&page=3. Consecutive pages were contiguous in time with zero overlapping row tuples, and offsets up to 6900 in a one-day window returned full correctly-ordered pages.
    - _evidence:_ Live 1-day window 2023-01-01T00:00:00.000..2023-01-02T00:00:00.000 sort=ASC: 300-row sample across pages 1-3 was non-decreasing in time with 0 shared tuples between adjacent pages; ps50/page5 == ps100/page3[:50] exactly; page=70 (offset 6900) returned N=100 spanning ~12 minutes; page=99 (offset 9800) returned 204.

- **[verified]** ORDER BY is on time alone with NO tiebreaker column, so the relative order of rows sharing an identical timestamp is formally undefined between queries. This makes offset-based paging theoretically unsafe exactly at a page boundary that falls inside a tie group. In practice modern data has microsecond timestamps and ties are absent (0 tie groups in a 200-row 2026 sample), but legacy whole-second data is full of them.
    - _evidence:_ ChatsController.java:234 (.orderBy(CHATS.TIME.sort(sort.toJooq()))) — single sort key; no PK exists to break ties (see chats-schema finding). Live 2013-11-18 100-row sample: only 93 distinct timestamps for 100 rows, 6 tie groups covering 13 rows.

- **[verified]** There is NO maximum window span. A 19-year window (2011-01-01 to 2030-01-01) was accepted and returned 200 immediately with the oldest rows in the database. Earliest chat data is 2013-11-18. There is also no enforced recency cutoff: the ~1-hour 'scraperTimeCutoff' guard exists in the source but its rejection bodies are commented out, so it has no effect.
    - _evidence:_ ChatsController.java:191 (scraperTimeCutoff computed) with :197-199 and :205-207 bodies commented out (// return ResponseEntity.status(HttpStatus.BAD_REQUEST)...). Live: 2011->2030 ASC returned 200, earliest three rows 2013-11-18T03:43:40Z / :41Z / :45Z.

- **[verified]** There is NO id, cursor, sequence, or primary key on chat rows — dedupe cannot be made trivial. The chats table has exactly four columns: time (timestamptz(6), NOT NULL), chat (text, NOT NULL), player_name (text, NOT NULL), player_uuid (uuid, NULLABLE). The generated jOOQ table class defines no getPrimaryKey/getKeys/getIdentity override, meaning no key exists in the database. The CSV data dump is a generic (time, data, table_name) shape and likewise exposes no row id.
    - _evidence:_ src/main/java/vc/data/dto/tables/Chats.java:44,49,54,59 — the only four createField calls, and no key/identity accessors anywhere in the class; src/main/java/vc/data/dto/tables/pojos/Chats.java has exactly these 4 properties. src/main/java/vc/data/dto/tables/GetUuidData.java:42,47,52 (TIME, DATA, TABLE_NAME) backing /dump/player in DataDumpController.java. JSON row keys live were always exactly ['playerName','uuid','time','chat'].

- **[verified]** player_uuid is nullable and IS null in older data — 12 of 100 rows in a 2013 sample had uuid: null. player_name, chat and time are NOT NULL. A dedupe key must therefore not assume uuid is present; fall back to playerName. In a 200-row 2026 sample, zero rows had a null uuid.
    - _evidence:_ Chats.java:59 (PLAYER_UUID declared SQLDataType.UUID with NO .nullable(false), unlike TIME/CHAT/PLAYER_NAME at :44,49,54). Live 2013-11-18 sample: nullUuid=12/100; live 2026-07-25 sample: nullUuid=0/200.

- **[verified]** TIMESTAMP TEXT IS NOT CANONICAL — Jackson trims trailing zeros from the fractional seconds, so the same instant can serialize with a varying number of fractional digits (0 through 6 observed) and the raw string is unsafe as a dedupe key component. Observed digit-count histograms: 2013 sample {0 digits: 100/100} (whole seconds, e.g. ...T03:43:40Z); 2023 sample {3: 264, 2: 34, 1: 2} (millisecond source data, zeros trimmed — e.g. 110ms renders as '.11'); 2026 sample {6: 182, 5: 17, 4: 1} (true microsecond source data).
    - _evidence:_ Live: 300-row 2023 sample, 100-row 2013 sample, 200-row 2026 sample analyzed for fractional-digit length. Concrete example from the 2023 window: a row rendered as 2023-01-01T00:00:14.11Z (2 digits) adjacent to 2023-01-01T00:00:12.873Z (3 digits).

- **[verified]** In modern microsecond-precision data the tuple (time, playerUuid) is already effectively unique: 0 duplicate (time,uuid) pairs and 0 duplicate (time,uuid,chat) triples across a 200-row 2026 sample and a 300-row 2023 sample. In legacy whole-second data the same tuple genuinely collides: the 2013 sample contained 2 distinct rows sharing the same (time, uuid) pair — same player, same second — though their chat text differed, so (time,uuid,chat) was still unique there.
    - _evidence:_ Live tie/dup analysis: 2026 era n=200 -> ts_ties=0, (t,uuid) collisions=0, exact(t,uuid,chat) dups=0; 2013 era n=100 -> ts_ties=6 groups/13 rows, (t,uuid) collisions=2, exact(t,uuid,chat) dups=0; 2023 era n=300 -> 300 distinct timestamps, 0 dups.

- **[verified]** CACHE HAZARD: /chats/window responses are cached per exact parameter set for 5 minutes (Caffeine, maximumSize=250, expireAfterWrite = cache.ttl.default-ttl = 5m; chatsWindow has no override). Re-requesting an identical URL 100 seconds later returned a byte-identical 12-row response even though ~100 seconds of new chat had certainly arrived. A collector that repeatedly polls one fixed 'startDate=X, no endDate' URL for the live edge will be served stale data for up to 5 minutes and will believe the server is quiet.
    - _evidence:_ ChatsController.java:141 (@Cacheable("chatsWindow")); src/main/resources/application.properties:46 (cache.ttl.default-ttl=5m) with overrides at :47-50 covering only queue/tablist/tablistInfo/worldtime; src/main/java/vc/config/CacheConfig.java:26 (maximumSize=250,expireAfterWrite=<ttl>). Live: identical open-ended ASC URL at T0 and T+100s both returned N=12 with newest=2026-07-25T20:37:13.404045Z; response time lists compared equal.

- **[verified]** The rate limiter is a GLOBAL 5-permits-per-second bucket shared by every caller of every @RateLimiter(name="main") endpoint (/chats, /chats/window, /chats/word-count, /dump/*, and more), with a 10-second acquire timeout. Rejections are HTTP 429 with a COMPLETELY EMPTY BODY and NO Retry-After header. Empirically, contention is severe and bursty: roughly 18% of my requests failed with 429 even while pacing at one request every 3-4 seconds, and because my client already retried up to 6 times with 5/10/15/20/25s backoff, each reported failure represents a saturated-bucket period lasting 75+ seconds.
    - _evidence:_ src/main/resources/application.properties:21-23 (resilience4j.ratelimiter.instances.main.timeoutDuration=10s, limitRefreshPeriod=1s, limitForPeriod=5); ChatsController.java:140 (@RateLimiter(name = "main")) — a resilience4j instance is process-wide, not per-IP. Live: ~16 429s across ~87 requests at 3-4s pacing; 429 responses had Content-Type absent and body length 0. First run at 1.15s pacing produced 9 consecutive 429s after one success.

- **[verified]** /chats/window queries Postgres directly via jOOQ and is essentially live — it is NOT served from the 3-minute-lagged DuckDB replica that /chats, /chats/search and /chats/word-count use. Newest row available was 32 seconds behind wall clock. So the window endpoint is a viable backfill source right up to the present instant.
    - _evidence:_ ChatsController.java:231-238 uses the injected DSLContext dsl against CHATS, and /chats/window carries no @Bulkhead("chats-ddb"); by contrast :56/:248/:280 annotate the DuckDB-backed endpoints, which read d_chats synced on a DUCK_DB_SYNC_INTERVAL (default 3 min) schedule per src/main/java/vc/data/duckdb/ChatsDuckDb.java:30,35. Live: DESC endDate=<UTC now> returned newest row 2026-07-25T20:18:28.550095Z against a request wall clock of 20:19:00 (32.4s).

- **[verified]** A live SSE stream exists at GET /feed/chats and carries NO rate-limiter annotation, making it the correct primary capture path with /chats/window reserved for gap backfill. Its record shape is (time, chat, playerName, playerUuid, component) — note it carries an extra 'component' field that /chats/window does not return, so a dedupe key must be computed only from the four fields common to both sources.
    - _evidence:_ src/main/java/vc/controller/FeedController.java:49-67 (@GetMapping("/feed/chats") returning SseEmitter, no @RateLimiter, sets X-Accel-Buffering: no) and :113-120 (1-minute heartbeat comments); src/main/java/vc/feed/dto/ChatsFeedRecord.java (5 components incl. component); vc/controller/ChatsController.java:50 (PlayerChat has only 4).

- **[verified]** sort is matched case-insensitively — sort=asc (lowercase) is accepted and behaves as ASC, thanks to Spring Boot's lenient enum converter. This also matches the enum's own lowercase JSON representation.
    - _evidence:_ src/main/java/vc/util/Sort.java (enum ASC, DESC with @JsonValue toValue() returning name().toLowerCase()); live sort=asc returned 200 with ascending order identical to sort=ASC.

## Unknowns
- Whether the sustained 429 periods come purely from the shared in-process resilience4j bucket (5/s global, 10s acquire timeout) or from an additional Cloudflare per-IP rule layered on top. The server header is 'cloudflare' and the empty-body/no-Retry-After shape matches resilience4j's default, but I could not isolate the cause without deliberately abusing the API. Practical impact is the same either way; the practical unknown is whether a well-behaved collector's effective sustainable rate is 1 req/s, 1 req/4s, or less.
- Behavior at very deep offsets. I verified consistency up to offset 6900 within a one-day window; I did not test offsets in the 10^5-10^6 range (e.g. paging a multi-month window by offset), so whether those degrade, time out, or trip the 10s rate-limiter acquire timeout is untested. Time-slicing instead of deep offsets sidesteps this entirely, which is what I recommend.
- Whether Postgres provides any de facto stable ordering for rows sharing an identical timestamp. There is no tiebreaker in the ORDER BY and no primary key, so it is formally undefined; I found zero ties in modern microsecond data, so I could not construct a live test of page-boundary behavior inside a tie group.
- The exact date at which stored precision changed from whole seconds (2013 data) to milliseconds (2023 data) to microseconds (2026 data). I sampled three eras, not the transitions. A backfill that reaches years back should treat fractional precision as fully variable rather than assuming a cutoff.
- The distribution of ingest lag — how long after a message is spoken on 2b2t it becomes visible via /chats/window. I measured a single point (~32s between the newest available row and wall clock), which conflates ingest lag with the natural gap between messages. This matters for choosing how far behind 'now' a backfill high-water mark should sit before it is considered final.
- Whether the commented-out 'migrate to /feed/chats' guard (which would 400 any window request whose anchor is within 1 hour of now) is likely to be re-enabled. The code is present and intentional, so a collector relying on /chats/window for near-real-time data is relying on a behavior the maintainer has already prototyped removing.
- What the SSE feed's 'component' field contains (likely the serialized chat Component JSON) and whether it is stable enough to be worth persisting alongside the four common fields.

## Build implications
- Format every bound as UTC wall-clock with SIX fractional digits and no zone suffix: strftime('%Y-%m-%dT%H:%M:%S.') + '%06d' % microseconds. Do not append 'Z' or an offset — they are parsed and then silently thrown away, so a local offset would query the wrong instant with no error. Never emit only 3 fractional digits for a cursor bound.
- Treat both bounds as INCLUSIVE. Do not attempt to make stitching exact by adding an epsilon to the cursor: adding +1ms provably drops rows (a row at .872508 vanishes when startDate is .873), and adding +1us is correct only if your cursor is already microsecond-exact and you trust that no second row shares that exact microsecond. The robust design is to set the next startDate to EXACTLY the last-ingested timestamp, accept that the boundary row(s) come back again, and let the dedupe key discard them.
- Backfill with sort=ASC, startDate=<last-ingested timestamp>, endDate=<gap end or omitted>, pageSize=100. After each page, do NOT increment `page`; instead set startDate to the last row's timestamp and reset page=1. Time-slicing keeps offsets tiny, is immune to offset drift from concurrent inserts, and avoids the untested deep-offset regime. The inclusive lower bound plus the dedupe key make the re-delivered boundary row harmless.
- Stop a backfill loop when EITHER HTTP 204 is returned OR len(chats) < pageSize. There is no total, no pageCount, and no next-cursor to consult, and a 200 with an empty array never occurs. Additionally guard against a non-advancing cursor: if a page's last timestamp equals the startDate you sent and every row deduped away, you have hit a tie group larger than pageSize — raise pageSize to 100 (already max) and, if still stuck, advance by +1 microsecond and log the potential loss.
- Use this dedupe key: sha256(str(microseconds_since_epoch) + '\x1f' + (playerUuid.lower() if playerUuid else 'name:' + playerName) + '\x1f' + chat). Two rules are load-bearing. (1) Parse the ISO time string to integer microseconds since epoch and key on that integer — NEVER on the raw string, because Jackson trims trailing zeros and the identical instant arrives as '.11' from one query and '.110000' from another. Pad the fraction to 6 digits before parsing, or use a real ISO parser. (2) Fall back to playerName when uuid is null (12% of a 2013 sample); uuid is nullable in the schema while playerName is NOT NULL.
- Collision risk of that key: negligible for modern data and acceptable overall. A false merge requires the same player to emit byte-identical text in the same microsecond — impossible for a single client that the scraper records as one insert. For pre-millisecond legacy data (whole-second timestamps, ~13% of rows in a 2013 sample share a timestamp) a genuine double-send of identical text within the same second would be collapsed to one row. Since the collector's job is backfilling gaps in a LIVE capture, it will only ever touch microsecond-precision data, where the key is effectively exact. Do not attempt a stronger key — there is no id, sequence, or primary key on the chats table to build one from.
- Disable automatic redirect-following on the HTTP client, or explicitly reject any response whose Content-Type is not application/json. A malformed date returns 302 -> / -> /scalar and, with redirects on, surfaces as HTTP 200 with an HTML page. Without this guard a date-formatting bug will look like a successful empty poll and silently stall the backfill forever.
- Handle three distinct non-success shapes, all with empty bodies: 400 (missing sort anchor, endDate<=startDate, pageSize>100 — a permanent bug in your request, do not retry), 302 (unparseable date — also a permanent bug, do not retry), and 429 (transient, retry). Only 429 should be retried. Log 400/302 loudly as programming errors.
- Build the 429 handler for sustained outages, not for single blips. The bucket is 5/s GLOBAL across all users of the API, so your throughput depends on strangers' traffic. Pace at roughly 1 request/second at most, retry 429 with exponential backoff plus jitter, and be prepared for stretches over a minute where every attempt is rejected. There is no Retry-After header to read and no body to parse, so backoff must be self-derived. Crucially: persist the backfill cursor to disk after every successfully ingested page so a 429 storm, a restart, or a host reboot resumes without re-walking the gap.
- Never poll a fixed URL for the live edge. Responses are cached 5 minutes per exact parameter set; I confirmed an identical URL returned byte-identical results 100 seconds apart while chat was flowing. Always advance startDate (which changes the cache key) between polls. Corollary: do not cache-poison your own high-water mark by querying a window whose endDate is 'now' — the incomplete result will be served back to you for 5 minutes.
- Use GET /feed/chats (SSE) as the primary live capture, not polled windows. It has no rate-limiter annotation, no cache, and sends a heartbeat comment every 60 seconds — treat a heartbeat gap of >90s as a dropped connection and reconnect. Reserve /chats/window strictly for backfilling the interval between the last row you ingested and the first row from the reconnected stream. Compute the dedupe key from only the four fields common to both sources (time, playerName, playerUuid, chat) and ignore the feed-only 'component' field, otherwise the same message arriving from the feed and from a window backfill will produce two different keys and be stored twice.
- Do not send pageSize=0 (returns 204, indistinguishable from 'no data'), pageSize=-1 (302 error path), or pageSize>100 (400). Always send an explicit pageSize=100; the default is 25, which would quadruple your request count against a scarce global rate limit.
- Do not issue a request when your computed gap has start == end — that returns 400, not an empty result. Check for and skip zero-width gaps before calling.
- Set a hard floor on backfill range so a corrupted or absent cursor cannot trigger a walk from 2013-11-18 (the earliest data) — there is no server-side maximum window span to protect you; a 19-year window is accepted without complaint. Clamp the lower bound to something like now minus 7 days and alert instead of silently attempting a full-history crawl.
