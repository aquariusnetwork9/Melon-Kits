# schema

Canonical on-disk schema for a live 2b2t chat corpus, reconciled against rfresh's 2025 bulk CSV dump, the api.2b2t.vc /dump/player CSV export, the open-source jOOQ database schema, and the SSE/REST JSON payloads

## Findings

- **[verified]** cdn.2b2t.vc/vcdb-2025.zip is 468,365,953 bytes and honors HTTP range requests (Accept-Ranges: bytes, served by Cloudflare, cf-cache-status DYNAMIC). Cloudflare 403s Python urllib's default User-Agent, so range fetches must go through curl (or a browser-like UA).
    - _evidence:_ curl -sI https://cdn.2b2t.vc/vcdb-2025.zip -> HTTP/1.1 200, Content-Length: 468365953, Accept-Ranges: bytes, Server: cloudflare. Same URL via urllib.request -> HTTP Error 403: Forbidden.

- **[verified]** The archive is NOT zip64 and NOT multipart: a single EOCD record at absolute offset 468,365,931 declares 7 entries, central directory size 579 bytes at offset 468,365,352, disk 0 of 0. No PK\x06\x06 (zip64 EOCD) or PK\x06\x07 (locator) signature exists in the last 200 KB.
    - _evidence:_ Parsed 200 KB tail (bytes 468165953-468365952) with struct: EOCD fields (sig=101010256, disk=0, cd_disk=0, disk_entries=7, total_entries=7, cd_size=579, cd_offset=468365352, comment_len=0); tail.rfind(b'PK\x06\x06') and rfind(b'PK\x06\x07') both returned -1.

- **[verified]** chats.csv is the FIRST member of the archive at local file header offset 0, stored with deflate (method 8), compressed size 172,660,076, uncompressed size 775,865,797 bytes (= 0.78 GB, matching the documented figure). Its raw deflate stream begins at absolute byte offset 67 (30-byte local header + 9-byte name 'chats.csv' + 28-byte extra field).
    - _evidence:_ Central directory parse from tail.bin: 'chats.csv method=8 csize=172660076 usize=775865797 lho=0'. Local header at offset 0 unpacked as sig=PK\x03\x04, flags=8, nlen=9, elen=28, name=b'chats.csv' -> data offset 30+9+28=67.

- **[verified]** The exact chats.csv header row and column order is: time,chat,player_name,player_uuid — four columns, snake_case, LF-terminated, no UTF-8 BOM.
    - _evidence:_ curl -r 0-399999 then zlib.decompressobj(-15).decompress(d[67:]) inflated 807,386 bytes; first 40 bytes repr = b'time,chat,player_name,player_uuid\n2025-0'. BOM check out[:3]==b'\xef\xbb\xbf' -> False. CRLF count 0, LF count 1962 in first 200 KB.

- **[verified]** chats.csv timestamps are raw PostgreSQL timestamptz text: 'YYYY-MM-DD HH:MM:SS[.f{1,6}]+00' — SPACE separator (not T), numeric '+00' offset (never Z, never +00:00), and VARIABLE-width fractional seconds because Postgres trims trailing zeros.
    - _evidence:_ Across 15,533 inflated data rows the fractional-second digit-width histogram was {6: 14025, 5: 1359, 4: 125, 3: 21, 2: 2, 1: 1}; set of trailing offset forms was exactly {'+00'}.

- **[verified]** chats.csv is standard RFC4180: fields are quoted only when they contain a comma or a quote, and embedded quotes are escaped by doubling. All sampled rows parse to exactly 4 fields, and no field contained a newline or carriage return.
    - _evidence:_ csv.reader over 15,534 inflated lines gave field-count histogram Counter({4: 15534}); 644 lines contained a double-quote character, and masked shapes showed the quote wrapping only the chat field when it embedded a comma; b'""' present in stream (doubled-quote escaping); any(newline in field) -> False.

- **[verified]** chats.csv rows are sorted ASCENDING by time, and in the sampled window no row had an empty chat, player_name, or player_uuid.
    - _evidence:_ First inflated data row timestamp is 2025-01-01 00:00:00.7xxxxx+00 and subsequent rows increase monotonically; counts of empty player_uuid / player_name / chat were all 0 across 15,533 rows.

- **[verified]** The 2025 archive contains 7 CSV members in this order with these uncompressed sizes: chats.csv (775,865,797), connections.csv (839,145,038), deaths.csv (455,750,097), restarts.csv (1,592), queuelength.csv (3,821,142), playercount.csv (3,558,933), queuewait.csv (189,840). All deflate.
    - _evidence:_ Full central-directory enumeration from tail.bin, 7 entries at local header offsets 0, 172660143, 396778427, 466317086, 466317755, 467313814, 468303949.

- **[likely]** public.chats declares no primary key, unique key, or index in the jOOQ-generated metadata, so byte-identical duplicate rows are structurally possible and the collector must supply its own dedup key.

    - _evidence:_ api/src/main/java/vc/data/duckdb/ChatsDuckDb.java line 42 (CREATE TABLE) and line 60 (INSERT ... SELECT *), line 79 INSERT INTO d_chats VALUES (:time, :chat, :player_name, :player_uuid).

- **[verified]** GET /dump/player does NOT return the chats.csv shape. It returns a MELTED three-column union across tables with header exactly: time,data,table_name — so it can never be concatenated with the bulk chats.csv without reshaping.
    - _evidence:_ Single request to https://api.2b2t.vc/dump/player?playerName=<known-player> returned HTTP 200, Content-Type: application/csv, Content-Disposition: attachment; filename="<Name>.csv", 5,995 bytes / 119 lines. First bytes repr = b'time,data,table_name\n2022-...'. csv.reader field-count histogram Counter({3: 119}).

- **[verified]** In the /dump/player CSV, table_name is a discriminator taking values chats, connections, deaths (69/45/4 rows for the sampled player), and the single `data` column holds the per-table payload string: the chat message for chats, a short join/leave token for connections, and the death message for deaths. There are NO player_name or player_uuid columns — identity is implicit in the request parameter.
    - _evidence:_ collections.Counter over column 2 = {'chats': 69, 'connections': 45, 'deaths': 4}; masked data shapes showed 4-5 letter tokens for connections rows and longer sentence-shaped strings for deaths/chats rows; parsed header list is ['time','data','table_name'].

- **[verified]** The /dump/player CSV uses a DIFFERENT timestamp format from the bulk dump: ISO-8601 with a T separator and a Z suffix, 'YYYY-MM-DDTHH:MM:SS[.mmm]Z'.
    - _evidence:_ Digit-masked distinct formats over 118 data rows: '9999-99-99T99:99:99.999Z' x107 and '9999-99-99T99:99:99Z' x11. Zero rows matched the bulk dump's 'YYYY-MM-DD HH:MM:SS.ffffff+00' pattern.

- **[verified]** The /dump/player export LOSES sub-millisecond precision relative to the bulk dump: every fractional timestamp carries exactly 3 digits (or none), whereas the same underlying chats table yields up to 6 digits in chats.csv. This is not chance — Java's OffsetDateTime.toString() emits fractional seconds in 3/6/9-digit groups, so true microsecond values would have rendered as 6 digits.
    - _evidence:_ Dump fractional widths were only {3: 107, none: 11} across 118 rows, versus bulk chats.csv widths {6,5,4,3,2,1} with 90% at 6 digits. Endpoint body is produced by Routines.getUuidData(...).formatCSV() at api/src/main/java/vc/controller/DataDumpController.java lines 69 and 78.

- **[verified]** The /dump/player CSV is sorted DESCENDING by time (newest first) as a single interleaved union across all three tables — not grouped by table and not ascending, the opposite of chats.csv ordering.
    - _evidence:_ Overall timestamp list equals sorted(reverse=True) -> True; ascending -> False. Run-length grouping of table_name showed 15 alternating runs (connections, deaths, chats, connections, ...) rather than 3 contiguous blocks.

- **[verified]** The /dump/player CSV shape is defined by a database-side routine get_uuid_data returning (time, data, table_name), rendered by jOOQ's Result.formatCSV().     - _evidence:_ api/src/main/java/vc/data/dto/tables/GetUuidData.java lines 42-52 declare TIME TIMESTAMPWITHTIMEZONE(6), DATA CLOB, TABLE_NAME CLOB; grep for get_uuid_data in *.sql outside the generated /dto/ tree returned no results.

- **[verified]** The /dump/player concurrency limit of 1 is confirmed in configuration, as is a 5-request-per-second global bucket on the main rate limiter — corroborating that this endpoint must be called serially.

- **[verified]** The SSE feed at GET /feed/chats emits ChatsFeedRecord as JSON with FIVE camelCase fields: time, chat, playerName, playerUuid, component. The `component` field exists ONLY on the live feed DTO — it is absent from the chats table, from chats.csv, and from every REST JSON response.

- **[verified]** The task's stated camelCase mapping is WRONG for the REST endpoints: /chats, /chats/search and /chats/window serialize the PlayerChat record whose UUID field is named `uuid`, NOT `playerUuid`. - **[verified]** No Jackson property-naming strategy is configured anywhere in the project, so Java field names pass through to JSON verbatim as camelCase and there is no snake_case JSON variant to reconcile.
    - _evidence:_ grep for NamingStrategy|naming-strategy|SNAKE_CASE|JsonProperty across src/main (*.java, *.yml, *.yaml, *.properties) returned zero matches; the only config file is src/main/resources/application.properties.

- **[verified]** The explicit field mapping across all four surfaces is: DB/bulk-CSV `time` = SSE `time` = REST `time`; `chat` = `chat` = `chat`; `player_name` = `playerName` = `playerName`; `player_uuid` = `playerUuid` = `uuid`; and `component` exists on SSE only with no DB or CSV counterpart.
    - _evidence:_ Composed from Chats.java lines 44-59 (DB), inflated chats.csv header row, ChatsFeedRecord.java (SSE), and ChatsController.java line 50 (REST).

- **[verified]** Postgres's trailing-zero trimming of timestamptz fractions is a REVERSIBLE transform in the store->export direction, which is what makes a fixed-width 6-digit canonical timestamp losslessly convertible back to the dump's exact text.
    - _evidence:_ Observed bulk-dump values include both 6-digit and shorter fractions (widths 1-6) and never a trailing zero in the short forms; therefore right-padding a short fraction with zeros to 6 digits and stripping them again reproduces the original byte-for-byte, and a zero fraction renders with no decimal point at all.

- **[verified]** Both CSV surfaces agree on file-level conventions: UTF-8 with no BOM and bare LF line terminators, so concatenation never needs newline normalization.
    - _evidence:_ chats.csv: BOM False, CRLF 0, LF 1962 in first 200 KB. dump.csv: BOM False, CRLF 0, LF 119.

## Unknowns
- Whether any of the full 6,701,781 chats.csv rows contain an embedded newline or carriage return inside the quoted chat field. The 15,533-row sample had none, but 2b2t chat can carry crafted payloads, so this cannot be ruled out from a 0.1% sample. Treat as possible and never line-split the CSV.
- Whether player_uuid is ever actually NULL in the historical data. It is nullable in the schema and ChatsDuckDb.java explicitly null-guards it, but 0 of 15,533 sampled rows were empty. The true null rate is unknown, which determines how often the UUID-keying fallback fires.
- Whether the millisecond truncation in /dump/player happens inside the DB routine get_uuid_data or in jOOQ's formatCSV()/OffsetDateTime rendering. The routine body is server-side and not in the repo. Either way the loss is observed, but the attribution is unconfirmed.
- Whether the SSE `component` field is always populated or is null for some message classes (e.g. plain player chat vs. system/death messages). Not determinable without a sustained live SSE capture, which was out of scope here.
- Whether pre-2025 bulk dumps (vcdb-2024.zip and earlier, if they exist at the same CDN path) use the identical chats.csv header and Postgres timestamp rendering. Only vcdb-2025.zip was probed. Column order is likely stable since it derives from SELECT * on a table with no migrations visible, but this is unverified.
- Whether /chats and /chats/search can serve as a practical backfill source at microsecond precision. The PlayerChat JSON carries an OffsetDateTime that Jackson may render with full precision (unlike the CSV path), but this was not fetched — only one API request was budgeted and it was spent on /dump/player as instructed.
- Whether public.chats truly lacks a primary key in the live database, or whether the jOOQ generator was simply configured to skip key generation for this table. The generated class carries no key metadata, which is strong but indirect evidence.
- The retention/ordering guarantees of the SSE feed on reconnect — whether it replays missed messages or drops them. This determines whether gap-filling from REST is mandatory after every disconnect.

## Build implications
- Write NDJSON: one JSON object per line, UTF-8, bare LF terminators, no BOM, no pretty-printing, no trailing comma. This matches both CSV surfaces' file conventions and lets the corpus be appended to and streamed. Partition files by UTC day (chats-YYYY-MM-DD.jsonl) and gzip closed days.
- Use exactly these canonical field names and types: ts (string, required), ts_us (integer, required), player_uuid (string|null, required key), player_name (string, required), chat (string, required), component (string|null), src (string enum, required), precision (string enum, required), row_id (string, required), ingest_ts (string, required). Emit keys in that fixed order on every line so the files diff and compress well.
- Store ts as ISO-8601 UTC with a FIXED width of exactly 6 fractional digits and a Z suffix: YYYY-MM-DDTHH:MM:SS.ffffffZ (e.g. 2025-01-01T00:00:00.730384Z). Never emit the variable-width form. Fixed width is the critical choice: it makes byte-lexicographic sort identical to chronological sort, which the bulk dump's variable-width Postgres format does NOT reliably guarantee once the +00 suffix collides with shorter fractions.
- Convert ts to the bulk dump's exact CSV text with this deterministic four-step rule, which is byte-lossless: (1) replace the T with a single space; (2) replace the trailing Z with +00; (3) strip trailing zeros from the 6-digit fraction; (4) if the fraction becomes empty, delete the decimal point as well. Verified against observed dump values which include 1-to-6-digit fractions and never a trailing zero.
- Also store ts_us as an integer count of microseconds since the Unix epoch. This gives the text-mining pipeline cheap range filtering, sorting, and windowing without parsing 6.7M+ timestamp strings, and it is the natural bucket key for rate/burst analysis.
- Set precision to "us" for rows from sse, proxy-log, and the bulk dump, and "ms" for rows from rest-backfill. This is mandatory, not cosmetic: /dump/player truncates to milliseconds, so a backfilled row's ts is a LIE below the millisecond (it will read .730000Z when the truth was .730384Z). Without this flag, downstream dedup will treat the two as distinct events and inter-message timing analysis will show spurious zero-microsecond clustering.
- Compute row_id as a hex-truncated SHA-256 over the tuple (ts truncated to MILLISECOND precision, player_uuid or the literal "@null", chat), joined by a byte that cannot occur in any field such as 0x1F. Truncate to milliseconds inside the hash specifically so that the same message seen live via SSE (microsecond) and later via rest-backfill (millisecond) collapses to ONE row. Since public.chats has no primary key, this collector-side id is the only dedup handle available.
- Key the corpus on player_uuid, never player_name. Treat player_name as a mutable observation valid only at ts, and if you need name history derive it as a separate (player_uuid, name, first_seen, last_seen) side table rather than trusting the name on any given chat row. Renames are the exact failure this prevents.
- Handle the nullable UUID explicitly: player_uuid is NOT NULL-constrained in the database, so allow JSON null and make every consumer's group-by tolerate it. Do not substitute the name into the uuid field as a fallback, and do not drop the row; use the literal "@null" sentinel only inside the row_id hash so null-uuid rows still dedup on (time, chat).
- Constrain src to exactly four values: "sse" (live /feed/chats), "rest-backfill" (/dump/player or /chats), "proxy-log" (your own AquariusProxy/ZenithProxy capture), and "bulk-dump-2025" (rfresh's chats.csv). Record it on every row so precision, completeness, and trust can be reasoned about per-source after the fact.
- Capture component from the SSE feed and persist it, because it is available NOWHERE else. It is absent from the chats table, from chats.csv, and from all REST JSON. If the collector drops it at ingest, the raw Minecraft chat component (colors, hover/click events, translate keys, and the distinction between player chat and system messages) is lost permanently. Set it to null for non-SSE sources rather than omitting the key.
- Read the SSE feed's UUID from the field playerUuid, but read the REST /chats, /chats/search and /chats/window responses from the field uuid. These are different names for the same value and the mismatch is silent — a single hardcoded accessor will produce a corpus of null UUIDs from whichever surface it guessed wrong. Normalize both into canonical lowercase hyphenated form on the way in.
- Do not attempt to concatenate /dump/player output with chats.csv. They share only the `time` column name and disagree on shape (3 melted columns vs 4 wide), timestamp format (T/Z/millis vs space/+00/micros), sort order (descending interleaved vs ascending), and identity (implicit in the query param vs explicit columns). To use it as a backfill source you must filter to rows where table_name == 'chats', map data -> chat, inject the requested player's uuid and name from the request context, re-sort ascending, and stamp precision "ms".
- Parse both CSVs with a real RFC4180 parser (Python's csv module or equivalent), never by splitting on commas or newlines. The chat field is quote-wrapped whenever it contains a comma and escapes embedded quotes by doubling, and embedded newlines cannot be ruled out across the full 6.7M rows.
- When emitting the dump-compatible CSV, write the header exactly as time,chat,player_name,player_uuid with LF terminators and no BOM, quote a field only when it contains a comma, a double quote, CR, or LF, and escape quotes by doubling. Sort ascending by ts. That reproduces rfresh's file conventions so downstream tools that expect the dump layout work unmodified.
- Range-fetch the CDN with curl or an explicit browser-like User-Agent, not Python urllib, which Cloudflare 403s. The recipe that worked and is reusable for the other members and future years: read the last ~200 KB for the EOCD, parse the central directory in place (it is only 579 bytes and lives inside that tail), then range-fetch from the member's local-header offset, skip 30 + name_len + extra_len bytes, and inflate with zlib.decompressobj(-15). No zip64 handling is required for this archive.
- Pace all api.2b2t.vc calls at 1 request/second or slower and serialize /dump/player strictly — its bulkhead allows exactly 1 concurrent call with a 10s queue wait, and the main limiter is 5 requests/second GLOBAL across all clients. Back off rather than retry on 429 or on a bulkhead rejection; a parallel backfill will starve other users and get throttled anyway.
- Record ingest_ts (collector wall clock, same ISO-8601 microsecond-Z format) separately from ts (the event time asserted by 2b2t.vc). The gap between them is your only signal for SSE lag, reconnect gaps, and clock skew, and you will want it when auditing which windows need REST gap-filling.
